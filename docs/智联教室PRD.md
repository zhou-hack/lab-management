### 1.2 涉及业务范围

本系统覆盖高校实训室与专业实验室的场地和预约管理，现行范围包括：

- **管理对象**：校内实训室、专业实验室、教室及其开放时段、维修窗口、节次占用和使用记录。
- **用户对象**：学生、老师、管理员与运维管理员；预置角色为 `STUDENT / TEACHER / ADMIN / OPS_ADMIN`。
- **业务范围**：
  - **认证与 RBAC**：账号密码登录、JWT 双 token、活动角色切换、菜单与权限装配、管理员数据范围；
  - **场地管理**：场地台账、容量、位置、开放窗口、状态、维修时段，以及 `facilities` 的“配套设备”自由文本说明；
  - **场地预约**：单次/周期预约、12 节次、跳选拆分、管理员一级审批、维修与占用拦截、签到签退和取消；
  - **共享单据与日志**：统一单号、审批与事件关联、附件和消息关联、操作日志审计；
  - **课程表集成（保留规划）**：实验室排课 Excel 批量导入，用于场地预约冲突检测与教室使用表生成。
- **对接预留**：与学校统一身份认证（SSO）、教务排课系统的对接能力预留；课表采用 Excel 导入轻量化方案。

涉及部门：教务处（课表数据提供方）、信息技术中心（技术支持）、各学院教学办（实验室管理，系统主要使用方）与设备处（业务管理）。

**业务范围明确边界：**

- 系统只做当前业务记录、流程流转、状态管理与统计分析；现场管理制度仍需学校线下配套执行；
- 不替代学校现有教务排课系统、校级资产系统与后勤综合报修系统，仅预留必要对接能力；
- 不改造、替换实验室原有硬件，不将物理门禁或 IoT 联动作为当前预约前置条件。

## 二、需求概述

### 2.1 业务背景

#### 2.1.1 当前业务现状与问题

我校各学院实训室与专业实验室的场地使用仍可能依赖纸质登记、微信群协调与人工记忆，主要问题包括：

1. **预约靠人工协调**：场地时段靠口头约定，课程、维修与预约之间容易冲突；
2. **审批缺少统一留痕**：申请、批准、驳回和取消分散在不同渠道，难以回溯；
3. **周期安排重复录入**：固定星期的教学或训练需要反复提交，操作成本高；
4. **使用过程难追踪**：签到、签退、取消与占用释放缺少统一口径；
5. **权限边界不清**：不同角色可见菜单、可操作单据和可管理数据范围需要统一控制。

#### 2.1.2 项目来源与定位

本项目由学生竞赛《智联教室》方案演进而来，当前聚焦场地资源与预约过程管理。

**项目定位：**

- 轻量化实验室场地与预约平台，采用独立部署模式，自建账号体系与标准数据库；
- 一套 Web 应用按登录角色呈现学生、老师、管理员和运维管理员视图；
- 系统只负责业务记录、流程流转、状态管理与统计分析，不替代学校线下管理制度；
- 一期范围限定为试点学院/实验室，后续迭代推广至全校。

#### 2.1.3 业务目标（可量化）

|目标|衡量指标|目标值（一期）|
|---|---|---|
|场地预约审批|提交到管理员审批结果平均时长|≤ 24 小时（工作时段）|
|冲突拦截|维修、课表或有效占用重叠被服务端拦截的比例|100%|
|跳选拆分|非连续节次被正确拆为独立连续段预约的比例|100%|
|周期展开|批准规则在有效日期内按星期和节次展开的准确率|100%|
|使用留痕覆盖率|审批、取消、签到、签退可追溯记录占比|100%|
|越权防护|无权限或越归属请求被后端拒绝的比例|100%|
|场地使用率|已约时段 / 开放时段|≥ 40%（试点期参考值）|

#### 2.1.4 业务名词说明

|业务名词|说明|
|---|---|
|实验室（实训室）|同一类物理空间的不同称谓；系统内统一以场地主档建模|
|场地预约|对整间场地的日期与节次进行排他性预约|
|单次预约|某一上海业务日期、同一场地的一段连续节次预约|
|周期预约|按固定星期、连续节次和起止日期重复展开的预约规则|
|节次|上海本地作息中的教学时间段，当前为 1–12 节（08:00–22:00）|
|跳选拆分|选择非连续节次后，按每个连续节次段分别创建预约单|
|维修窗口|场地暂停开放的时段；提交和批准均须检查重叠|
|签到签退|预约人对已批准预约执行的使用开始与结束操作|
|共享单据|统一承载单号、归属、幂等键、审批、事件、附件和消息关联的公共单据底座|
|活动角色|一人多角色时，当前 token 与菜单权限实际采用的角色视图|
|数据范围|管理员可读取或写入的数据边界，一期为 ALL/DEPARTMENT + READ/WRITE|
|SSO统一身份认证|学校统一的单点登录体系，用于校内账号一键登录|

### 2.2 用户与角色

**概念区分：** **用户 = 谁**（登录账号的主体身份）；**角色 = 能干什么**（权限集合）。本系统共 **3 类用户、4 个预置角色**。

#### 2.2.1 用户类型（账号主体）

|用户|说明|登录方式|默认持有角色|第一阶段是否开放|
|---|---|---|---|---|
|学生|使用实验室的在校学生|账号密码（管理员预建账号）|STUDENT|✅|
|老师|实验室授课老师|账号密码（管理员预建账号）|TEACHER|✅|
|管理员|实验室审批、场地与配置的统一管理人员|账号密码|ADMIN；OPS_ADMIN 仅 SQL 预置|✅|

#### 2.2.2 角色定义（权限集合）

|角色|角色描述|核心诉求|权限范围|挂载用户|第一阶段是否开放|
|---|---|---|---|---|---|
|STUDENT|使用实验室的在校学生|便捷预约场地并追踪本人记录|查询场地；提交单次/周期预约；查看、取消本人预约；按已批准预约签到签退；查看老师推送给本人的物料代领任务；不可访问系统管理后台|学生|✅|
|TEACHER|实验室授课老师|为实验课快速完成场地准备|与学生使用同一预约流程和管理员一级审批链；可关联课程、班级信息；可指定学生助理并将本人原申领单推送学生代领；无额外初审或背书权限|老师|✅|
|ADMIN|实验室业务管理员|场地、维修、审批与业务日志统一管理|场地台账和维修窗口维护；全部预约查询和一级审批；场地使用记录与统计；仅查看业务模块操作日志；受数据范围约束|管理员|✅|
|OPS_ADMIN|最高级运维管理员|系统配置、人员权限与全量审计|仅绑定 system 模块权限和 system% 菜单，不参与场地、预约、物料等业务流程；不受数据范围约束；角色自身仅 SQL 预置且权限绑定锁定|仅 opsadmin|✅|

> **用户 ↔ 角色挂载规则：**
> - 学生、老师、管理员的主身份角色由服务端按账号主体确定；老师可经系统管理叠加绑定 ADMIN。
> - 一人多角色时默认以主身份角色登录，可在实际持有角色间切换；切换由服务端校验并重签双 token。
> - 学生助理只是老师在物料域内对具体学生的限时业务授权，不是新增角色；学生只能查看本人被委派的原申领，实际出库仍由库位管理员执行。
> - OPS_ADMIN 不可通过页面创建、转授或提升；普通管理员不能接管 opsadmin 账号。

> **身份认证规划：**
> - **一期（本期）**：统一账号密码登录，前端按账号取盐并复算 BCrypt 哈希后提交；JWT access/refresh 双 token。
> - **二期（预留）**：校园 SSO 统一身份认证（首选）> 飞书免密登录。
> - 人脸识别如未来评估，只能作为可关闭的可选方式，不得作为唯一登录手段。

|---|---|---|
|预约冲突频发|微信群口头协调，课程、维修和预约信息分散|统一节次与占用模型，提交和批准双重校验|
|周期安排繁琐|每周重复填写相同预约|周期规则一次审批，按日期自动展开|
|审批与取消难追踪|过程分散，责任人和时间不清|共享单据、事件与操作日志全程留痕|
|越权操作风险|只隐藏按钮或直接信任客户端身份|后端功能权限、数据范围和单据归属强制校验|
|时间口径不一致|本地日期、节次和 UTC 混用|上海业务日历与 UTC 时间点明确分层|

### 2.4 需求价值

1. **冲突可控**：课程、维修和有效预约使用统一校验，避免重复占用；
2. **操作提效**：跳选和周期预约减少重复录入，管理员一级审批缩短链路；
3. **过程可溯**：审批、取消、签到签退、维修与权限变更均有记录；
4. **权限清晰**：四角色、活动角色和数据范围共同约束功能与数据；
5. **时间一致**：页面按上海时区展示，服务端和存储统一 UTC。

**升级预留设计（关键）：**

|抽象层|一期实现|二期扩展|切换方式|
|---|---|---|---|

### 3.2 核心业务主流程

```Plain Text
# 单次场地预约
学生/老师选择日期与场地 → 查看全部场地总览或单场地 1–12 节次
  → 点按多选（可跳选）→ 填写用途与人数
  → 系统校验开放窗口、场地状态、维修与有效占用
  → 按连续节次段拆分创建 PENDING 预约
  → 管理员一级审批（批准前重验）
  → APPROVED 写入占用 / REJECTED 留档
  → 本人签到（派生 IN_USE）→ 签退或 end_at+2h（派生 FINISHED）

# 周期场地预约
学生/老师选择场地、固定星期、连续节次和起止日期
  → 提交周期规则 PENDING → 管理员同一级审批
  → 批准后逐周展开并逐次重验冲突 → 写入各周占用
  → 各展开单独立签到签退、取消和留痕

# 取消
本人对待审批或符合时间条件的已批准预约发起取消
  → 服务端复核归属与当前状态 → CANCELLED
  → 释放可释放占用，保留取消原因与事件
```

**流程异常分支说明：**
- **维修冲突**：待审期间新增维修或维修范围变化时，批准必须失败；不能仅依赖提交时结果；
- **预约冲突**：同一场地同一时段已有有效占用时，提交或批准被拦截，不自动抢占；
- **并发批准**：两个待审批单先批先得，后批在锁内重验后失败；
- **过期审批**：开始时间已过仍未审批的预约不能批准，按当前规则过期取消或驳回；
- **取消与审批竞争**：状态条件更新保证只有合法流转成功，不重复写入或释放占用；
- **跳选误合并**：非连续节次不得合并为一个覆盖未选节次的大区间。

#### 业务对象关联关系说明

|表名|用途|
|---|---|
|sys_user / sys_role / sys_permission|用户、四角色、权限及关联关系|
|sys_user_data_scope|管理员 ALL/DEPARTMENT 与 READ/WRITE 数据范围|
|lab|场地名称、类型、位置、容量、facilities、开放窗口、状态与可见性|
|class_period|1–12 节次的上海本地起止钟表时间|
|lab_maintenance_window|场地维修窗口与原因|
|lab_booking|单次预约或周期展开后的预约单，含日期、连续节次、UTC 起止与状态|
|lab_booking_series|周期规则、有效日期、申请人、幂等键与审批状态|
|lab_slot|已批准预约或正式课次形成的占用及释放信息|
|lab_usage|预约签到、签退与归档记录|
|biz_document|统一单号、单据类型、归属与幂等键|
|approval_task / document_event|审批待办与不可变过程事件|
|sys_operation_log|认证、权限、场地、预约和系统管理操作审计|
|course_schedule / schedule_occurrence|保留规划：课程排课规则与实际课次|

**业务对象关联关系：**

|对象|关联关系|
|---|---|
|场地 ↔ 预约|一对多；同一时段仅允许一个有效占用|
|周期规则 ↔ 预约单|一对多；每个展开单回指来源规则|
|预约 ↔ 使用记录|一对一；保存签到签退与结束信息|
|预约/课次 ↔ 占用|按来源恰一关联，释放后不再参与冲突|
|共享单据 ↔ 审批/事件|一对多；统一使用 document_id 关联|
|用户 ↔ 角色 ↔ 权限|显式持有关系；活动角色决定当前权限与菜单装配|

### 3.3 角色业务流程

|步骤|操作角色|动作|
|---|---|---|
|1|学生/老师|查询场地和节次，提交单次或周期预约，可跳选并由系统拆单|

|6|管理员/运维管理员|按权限查询业务或全量日志；运维管理员维护系统管理数据|

## 四、详细功能需求

### 模块一：学生视图

#### 4.1.1 场地预约申请

**功能说明：** 学生可为竞赛训练、课程设计、社团实验等用途提交整间场地的单次或周期预约，所有申请只经管理员一级审批。

**操作流程：**

|步骤|操作|说明|
|---|---|---|
|1|进入场地预约|查看日期内全部场地总览，或选定场地查看 1–12 节次|
|2|选择节次|点按 toggle 多选，可连续也可跳选；维修覆盖节次不可选|
|3|填写预约信息|用途、人数；周期预约另填重复规则与起止日期|
|4|提交|服务端重验后创建 PENDING；跳选按连续段拆单|
|5|查看结果|管理员批准为 APPROVED，驳回为 REJECTED；详情展示过程记录|

**业务规则：**
- 人数不得超过场地容量，日期与节次必须落在开放窗口内；
- 待审批不永久占用，批准时再次检查冲突；
- 学生不能指定或执行额外审批，不设置教师背书环节。

#### 4.1.2 我的预约与使用记录

**功能说明：** 学生查看本人单次、周期及展开预约，按允许条件取消、签到和签退。

**业务规则：**
- 只能查看和操作本人记录，不能通过遍历 ID 获取他人单据；
- 待审批或已批准且符合取消时间条件的预约可取消，取消后保留原因和事件；
- 已批准预约签到后显示使用中，签退或归档后显示已结束；
- 记录保留周期与学校档案要求一致。

### 模块二：老师视图

#### 4.2.1 场地预约发起

**功能说明：** 老师为实验课、实训周、竞赛训练、科研活动等用途申请场地；与学生使用同一管理员一级审批链。

**业务规则：**
- 可填写课程名称、班级、用途和人数；周期预约用于固定星期和连续节次的重复安排；
- 单次可跳选，周期规则自身使用连续起止节次；每个展开日仍逐次校验维修和占用；
- 老师没有额外初审、背书或自动通过特权。

#### 4.2.2 我的预约与课程关联

- 查看、取消本人预约并执行签到签退；
- 课程关联只用于业务说明和后续课表冲突检测，不据此扩大数据范围；
- 课程名单关联数据按 RBAC 数据范围规则计算，老师不能查看无关学生的私人预约。

### 模块三：管理员视图（PC 优先）

#### 4.3.1 场地台账与维修管理

**功能说明：** 维护场地主档、开放窗口、状态与维修时段。

**核心字段：**

|字段|说明|
|---|---|
|lab_name / lab_type|场地名称与类型，名称全局唯一且删除后不复用|
|location_detail|位置自由文本|
|capacity|容纳人数，必须大于 0|
|facilities|“配套设备”自由文本说明，不生成独立业务关系|
|open_start / open_end|每日上海本地开放窗口，start < end|
|visible / status|可见性，以及 AVAILABLE/MAINTAINING/CLOSED 主档状态|
|维修窗口|起止 UTC 时间与原因；参与预约提交和批准的重叠校验|

**操作能力：** 新增、编辑、启用、停用、批量启停、导入导出、逻辑删除与引用检查；维修窗口维护不得被预约批准绕过。

#### 4.3.2 场地预约审批

**功能说明：** 统一处理单次和周期预约的唯一一级审批。

**业务规则：**
- 待办按提交时间展示，可按类型、场地、日期和状态筛选；
- 批准前在事务内锁定场地并重验开放窗口、维修窗口与有效占用；
- 周期批准后按规则展开，逐周复查；驳回须填写意见；
- 所有审批动作写入过程事件和操作日志，结果通知申请人。

#### 4.3.3 场地使用记录与统计

- 查看预约、签到签退、取消、占用与释放记录；
- 教室使用表周视图（保留规划）：合并展示课表占用与预约占用；
- 统计场地预约率、使用率和审批效率，明确是否包含课表及无签到数据的统计口径；
- 管理员可按业务需要处理冲突，但不得直接改写历史事件或操作日志。

#### 4.3.4 业务操作日志

ADMIN 仅查看业务模块日志，不含 system/auth 系统管理日志；支持按操作人、模块、动作和时间分页，日志只追加不删除。

### 模块三A：老师助理与学生代领

**功能说明：** 老师可指定启用学生为限时代理助理，并在本人物料申领提交后、首次实发前，将原申领单推送、改派给学生或撤回代领。

**业务规则：**
- 助理授权保存师生、有效期和撤销历史，不形成新的系统角色；只有授权老师本人可以撤销。
- 委派不生成代领子单，不改变原申领的管理员一级审批、预占和库存业务链；审批通过前学生只能看到待办，不能领取。
- 学生只能查看本人被委派原单的物料、预约时间和计划领取库位，不能审核、实发或归还。
- 库位管理员实发时再次核验授权有效期、撤销状态和学生启用状态，并记录实际领取人；失效后须由老师改派或恢复本人领取。
- 授权撤销或过期不阻断已有出库的归还，不删除授权、委派、出库或归还历史。

### 模块四：基础支撑

#### 4.4.1 账号与权限管理

**功能说明：** 管理账号、角色、权限、菜单和数据范围。

**登录方式：**
- 全部用户统一账号密码；
- 前端先 GET /auth/salt 获取该账号 BCrypt 盐前缀，复算哈希后上传；服务端常量时间比对；
- JWT access 2 小时 + refresh 7 天，刷新轮换双 token；连续 5 次密码错误锁定 30 分钟；
- 二期可扩展校园 SSO 或飞书免密登录。

**权限模型：**
- 基于角色的访问控制（RBAC），权限标识为 `模块:资源:操作`；
- 预置角色仅为 ADMIN/TEACHER/STUDENT/OPS_ADMIN；一期不支持自定义角色和字段级权限；
- 多角色用户按活动角色装配权限和菜单，switch_role 校验实际持有关系；
- 管理员数据范围一期为 ALL/DEPARTMENT + READ/WRITE，无范围记录不自动获得全校数据；
- 操作日志记录操作人、时间、IP、变更前后值，敏感凭据不得入日志。

#### 4.4.2 共享单据与文件服务

**共享单据：** 统一登记 document_no、document_type、owner_user_id 和 idempotency_key；审批、事件、附件和消息使用 document_id 关联。业务状态以所属业务表为准，过程事件只追加。

**文件服务：** 保存经评审登记的业务附件；文件本体与业务数据分离，访问必须鉴权，上传限制大小和类型。历史文件不因单据取消或驳回而物理删除。

#### 4.4.3 消息推送

**消息类型：**
- 场地单次/周期预约提交、批准与驳回通知；
- 预约过期、取消、维修或占用冲突提示；
- 签到签退与归档结果通知；
- 系统管理和权限变更的必要审计通知。

**业务规则：**
- 一期站内信为主，紧急消息可叠加短信/邮件；二期可扩展飞书机器人；
- 发送通过事务发件箱和去重键重试，不在主事务中假装外部发送已原子完成；
- 消息模板统一管理，渠道无关。

### 模块五：场地预约详细规则

#### 4.5.1 单次、跳选与周期预约

- **单次预约**：同一上海日期、同一场地、同一连续节次段一张单；
- **跳选拆分**：多个不连续选择按连续段分别建单，每单独立审批和取消；
- **周期预约**：固定星期、连续节次、起止日期与用途形成规则，批准后展开；
- **12 节次**：当前使用 1–12 节（08:00–22:00），节次时间为上海本地 CLOCK，实际 start_at/end_at 为 UTC；
- **人数与开放窗口**：人数 ≤ capacity，预约时间必须在开放窗口内；
- **冲突区间**：统一使用 `[start_at, end_at)` 半开区间，端点相接不算冲突。

#### 4.5.2 维修与占用拦截

1. 前端将维修覆盖节次置灰，仅作为体验提示；
2. 后端在单次提交、单次批准、周期提交、周期批准四入口统一检查维修重叠；
3. 有效占用来自未释放的 lab_slot 及正式课次；PENDING 不永久占位；
4. 批准时在事务与场地锁内重验，后批准者遇冲突失败；
5. 维修窗口或课表后变更时，按当前实现生成冲突提示或待处理记录，不直接删除已有预约。

#### 4.5.3 审批、签到签退与取消

- 学生和老师均为 `PENDING → 管理员一级审批 → APPROVED / REJECTED`；
- 已批准预约由本人签到，使用记录保存 actual_start_at，运行阶段派生 IN_USE；
- 本人签退保存 actual_end_at，或超过 end_at+2h 后派生 FINISHED；
- end_at 是资源释放边界，归档宽限不额外占用后续时段；
- 待审批或已批准且符合时间条件的本人预约可取消；取消释放可释放占用并保留原因；
- 已驳回、已取消单据不可直接改回审批中，变更需求应新建预约。

#### 4.5.4 状态机

```Plain Text
PENDING ──管理员批准（重验通过）──> APPROVED ──本人签到──> IN_USE（派生）
   │                                  │                         │
   │                                  │                         ├─本人签退──> FINISHED（派生）
   │                                  │                         └─超过 end_at+2h──> FINISHED（派生）
   ├─管理员驳回──> REJECTED            └─有效取消──> CANCELLED
   └─有效取消或过期处理──> CANCELLED
```

周期规则使用 PENDING/APPROVED/REJECTED/CANCELLED；批准后展开的预约复用上述状态机。

### 模块六：实验室排课与课程表集成（保留规划）

> **设计动机**：正式教学排课时段，实验室不可对外开放预约。课程表模块作为场地预约冲突检测的数据源，并提供课表变更后的反向冲突提示。

#### 4.6.1 模块概述

|场景|用户角色|典型操作|
|---|---|---|
|批量导入实验室排课|管理员|课表管理 → 下载 Excel 模板 → 填写后上传 → 系统解析并入库 → 返回成功/失败报告|

|字段|类型|说明|
|---|---|---|
|schedule_id|ID|排课记录 ID|
|lab_id|ID|直接关联 lab|
|teacher_id|ID|关联 sys_user，必须是老师角色|

#### 4.6.3 节次时间表

#### 4.6.4 课程表 Excel 导入与手工维护

**导入流程：**
1. 管理员上传 Excel；

4. 使用文件哈希和稳定 external_row_key 防重复发布，不靠行号猜测身份；
5. 入库后检测与已生效预约的冲突，生成提示或待处理记录。

**手工维护：** 支持按学期对排课记录增删改，变更同样触发冲突检测；不得直接覆盖已有有效预约。

> 「—」表示该角色无此功能入口。OPS_ADMIN 不持有业务菜单或业务接口权限，不能直接调用接口绕过界面限制。

### 5.2 数据范围规则

- **学生**：仅本人预约与使用记录，以及本人被委派的物料代领原申领；场地目录按可见、启用和可约状态查询，代领不能通过遍历 ID 获取他人任务。
- **老师**：本人数据 + 所授课程关联数据；本人预约的取消、签到签退按单据归属校验。
- **管理员**：按归口部门划分数据范围；设备处管理员可为全校场地与预约数据，学院管理员为本学院数据；跨归口数据需显式 READ 范围，写操作需 WRITE。
- **运维管理员**：不受数据范围约束，无需登记范围行。

### 5.3 权限隔离规则

1. 所有受保护接口在服务端校验功能权限；管理员写操作再校验数据范围，前端隐藏入口不作安全依据。
2. 学生、老师的详情、取消、签到、签退须校验本人归属；管理员审批还须校验范围和当前状态。
3. 管理员与运维管理员的关键操作全部写入操作日志，含操作人、时间、IP、变更前后值。
4. JWT access 2 小时、refresh 7 天；敏感操作按策略要求二次密码确认。
5. OPS_ADMIN 仅 SQL 预置，其账号仅本人可编辑/启停/重置；角色权限绑定锁定，其余 3 个预置角色可由 OPS_ADMIN 整集替换权限。

## 第六章 非功能需求

### 6.1 性能需求

| 指标 | 目标值 |
| --- | --- |
| 移动端页面首屏加载 | ≤ 2s（4G 网络） |
| 管理后台列表查询（10 万级数据） | ≤ 1.5s |
| 场地预约冲突检测（含维修与课表比对） | ≤ 800ms |
| 并发能力 | 支持 500 在线用户，预约高峰期（选课周）1000 QPS |
| 周期展开与定时归档任务 | 单次执行 ≤ 5 分钟，支持幂等重试 |

### 6.2 兼容性需求

- 一套响应式 Web 应用（三端合一）：PC 优先，分辨率 ≥ 1366×768 提供完整功能，手机浏览器自适应保证核心流程可用；
- 学生视图/老师视图（移动端浏览器）：微信内置浏览器、Safari（iOS 12+）、Chrome（Android 8+）；
- 管理员视图（PC）：Chrome 90+、Edge 90+；
- 不同浏览器时区下，上海日期、节次与 UTC 展示必须一致。

### 6.3 安全需求

1. 全站 HTTPS；敏感字段（手机号、密码）加密存储与传输，密码 BCrypt 哈希。
2. 接口鉴权：Token（JWT）+ 角色 + 数据范围三级校验；防 SQL 注入、XSS、CSRF。
3. 文件访问必须鉴权，不公开永久未授权 URL。
4. 越权防护：所有详情/操作接口校验数据归属（本人/数据范围），禁止通过遍历 ID 越权访问。
5. 限流：登录接口单 IP 每分钟 ≤ 10 次；预约提交单用户每分钟 ≤ 5 次，防恶意刷占。

### 6.4 合规需求

- 符合《个人信息保护法》：收集信息最小化（学号、姓名、手机号、人脸/指纹等生物信息不采集）；用户注销后个人信息匿名化，业务流水保留（审计要求）。
- 业务附件只用于对应业务与审计，按学校保存期限清理。
- 满足学校信息系统等级保护二级要求（日志留存 ≥ 6 个月）。

### 6.5 可用性需求

- 核心流程（查询→提交→审批→使用）入口清晰，跳选和周期规则给出明确反馈；
- 审批驳回、强制取消等关键操作必须填写原因并二次确认；
- 系统故障时降级：预约列表展示缓存数据并提示"数据可能延迟"，禁止写入；消息推送失败重试 3 次后落库待人工处理。

### 6.6 埋点需求

| 埋点事件 | 关键属性 |
| --- | --- |
| 单次预约提交/批准/驳回 | 场地 ID、连续节次、审批时长、是否跳选拆分 |
| 周期规则提交/批准/展开 | 规则 ID、展开数量、冲突数量、耗时 |
| 维修窗口创建/修改/停用 | 场地 ID、起止时间、影响预约数 |
| 签到/签退/归档 | 预约 ID、操作人、时间、结束方式 |
| 预约取消 | 预约 ID、取消人类型、取消原因、占用释放结果 |
| 活动角色切换 | 用户 ID、原角色、目标角色、是否成功 |
| 数据范围变更 | 操作人、目标用户、范围类型、访问模式 |
| 看板访问 | 看板类型、访问角色 |

### 6.7 日志需求

- 业务操作日志：预约、审批、签到签退、取消、维修与配置变更全量记录（操作人/时间/IP/参数/结果）；
- 系统运行日志：定时任务执行明细、消息推送结果、第三方接口调用（短信/统一认证）；
- 错误日志：异常堆栈 + 请求上下文，对接告警（错误率 > 1% 时通知运维）。

## 第七章 兼容与约束

### 7.1 系统定位边界

4. 历史版本功能如需追溯，查阅独立历史资料，不在当前系统提供已删除模块入口。

### 7.2 外部依赖

| 依赖 | 说明 | 降级方案 |
| --- | --- | --- |

| 短信/邮件通道 | 必要业务通知 | 应用内消息替代，失败自动降级并重试 |

### 7.3 数据约束

- 预约人数必须大于 0 且不超过场地容量；节次必须在 1–12 且 start ≤ end；
- 单次与周期展开均采用半开区间；纯日期、上海钟表时间与 UTC 时间点不得混存；

### 7.4 技术约束

- **前后端不分离**：采用后端模板渲染（服务端直出页面），不单独建设前端 SPA 工程与独立 API 层；
- **三端合一**：一套 Web 应用按登录角色呈现学生视图/老师视图/管理员视图，响应式布局 PC 优先、手机浏览器自适应；
- 不开发独立 H5 站点与原生 App。

## 附录 A 典型场景

### 场景 1：单次跳选与一级审批

1. 学生 A 选择下周三的某实训室，勾选第 1、2、4 节并填写用途与人数；
2. 系统将第 1–2 节和第 4 节拆为两张 PENDING 预约，不把第 3 节包含进占用；
3. 管理员批准前重验：第一张通过并写入占用，第二张若与新增维修重叠则批准失败并提示；
4. 学生对已批准预约签到、签退，过程可通过共享单据与日志追踪。

### 场景 2：周期预约与冲突重验

1. 老师 C 提交本学期每周二第 5–6 节的周期规则，状态 PENDING；
2. 管理员执行同一级审批，批准后系统逐周展开；
3. 某周存在正式课次或维修窗口时，系统按当前规则报告冲突，不覆盖原占用；
4. 各展开单保留来源 series_id，可分别签到签退和按规则取消。

### 场景 3：取消与审批竞争

1. 学生 A 的预约仍处于 PENDING，本人发起取消，同时管理员点击批准；
2. 服务端在状态条件与锁内处理，只有当前状态允许的操作成功；
3. 若取消先成功，则批准失败；若批准先成功，则取消按已批准预约规则重新判断；
4. 最终不重复写入占用，取消与审批过程均保留记录。

## 附录 B 主要状态机速览

### B.1 场地主档

`AVAILABLE ↔ MAINTAINING`；`AVAILABLE ↔ CLOSED`；维护与关闭状态可按管理规则互转。场地状态与实时节次占用分开维护。

### B.2 单次预约单

`PENDING →（管理员批准）→ APPROVED`；`PENDING →（管理员驳回）→ REJECTED`。
`PENDING / APPROVED →（有效取消或过期处理）→ CANCELLED`。
`APPROVED →（本人签到）→ IN_USE（派生）→（签退或超过 end_at+2h）→ FINISHED（派生）`。

### B.3 周期预约规则

`PENDING →（管理员批准并展开）→ APPROVED`；驳回为 `REJECTED`，有效取消为 `CANCELLED`。展开单复用 B.2。

## 附录 E 验收标准

### E.1 功能验收

| 编号 | 验收项 | 验收标准 |
| --- | --- | --- |
| AC-01 | 四角色与活动角色 | 仅 ADMIN/TEACHER/STUDENT/OPS_ADMIN；切换校验持有关系，越权请求返回 403 |
| AC-02 | 单次预约与跳选 | 1–12 节次可多选、跳选；非连续选择正确拆单，不占用未选节次 |
| AC-03 | 周期预约 | 与学生/老师相同的管理员一级审批；按星期和日期正确展开，重复执行不重复建单 |
| AC-04 | 维修与占用拦截 | 单次/周期提交和批准四入口均拦截维修重叠；并发批准不重复占用 |
| AC-05 | 签到签退与取消 | 本人归属校验有效；状态和时间条件不满足时拒绝；取消释放可释放占用并留痕 |
| AC-06 | 场地状态 | AVAILABLE/MAINTAINING/CLOSED 与实时占用分离；维修和关闭状态按规则阻止预约 |
| AC-07 | 数据范围 | 无范围记录不自动获得全校数据；READ/WRITE 与 ALL/DEPARTMENT 按矩阵执行；OPS_ADMIN 豁免正确 |
| AC-08 | 共享单据与日志 | 单号、审批、事件、附件/消息关联一致；历史只追加，敏感凭据不入日志 |
| AC-09 | UTC 与上海日历 | 时间点 UTC 三位毫秒，上海日期与节次换算正确；午夜和不同浏览器时区用例通过 |

### E.2 非功能验收

- 性能：满足 6.1 指标，重点实测冲突检测、周期展开和列表查询；
- 安全：无高危越权，未授权详情与写操作均被后端拒绝；
- 兼容：6.2 所列浏览器核心流程可用；
- 试运行：试点 4 周核心流程可用性 ≥ 99%，无 P0/P1 级遗留缺陷。

维修工单、巡检任务、6S 评分、维修知识库、IoT 联动、原生 App、多语言及尚未正式对接的外部认证/教务接口。
